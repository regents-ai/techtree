# 0. Executive implementation decision

The three slices implement one complete **development-only local product loop**:

```text
Resolved public Climb graph
        ↓
candidate skill snapshot
        ↓
Campaign-derived baseline and candidate manifests
        ↓
controlled manifest comparison
        ↓
immutable submission draft
        ↓
explicit DataPolicy acknowledgement
        ↓
idempotent run claim
        ↓
detached worker
        ↓
event-sourced run lifecycle
        ↓
development validation provider
        ↓
fake baseline and candidate episode receipts
        ↓
development-only UpliftReport
        ↓
CLI status, logs, cancellation, and result
```

The loop must be real in every product-control sense and fake only in the one place explicitly declared fake:

```text
No model is called.
No Hermes subject is launched.
No Docker subject is launched.
No Verifiers eval is run.
Rewards are generated by FakeRunExecutor.
```

Everything else is production-shaped:

```text
Campaign lineage
DataPolicy binding
skill immutability
manifest construction
mutation enforcement
confirmation
policy acknowledgement
detached process lifecycle
event ordering
state reconstruction
cancellation
artifact persistence
typed CLI JSON
```

The result must always say:

```text
execution_backend: fake
proof_grade: development_only
publication_eligible: false
```

A green PR8 proves that the future Hermes plugin can safely drive the CLI and that a real Verifiers executor can later replace the fake executor without redesigning draft, run, state, or CLI contracts.

# 1. Binding boundaries

## 1.1 Campaign versus Climb

`CampaignSpec` owns the scientific contract:

```text
taskset and committed membership
publisher validation commitment
environment
named subject agent
model
sampling
harness
runtime
mutation contract
evaluation backend
execution limits
scoring
evidence requirements
budgets
DataPolicy digest
optional ProgramRef
optional OutcomeContract digest
```

`ClimbManifest` owns public-product context:

```text
public identity
slug and version
title and summary
status and schedule
candidate policy
publication policy
leaderboard policy
CampaignSpec digest
```

PR6 consumes a `ResolvedClimb` graph and constructs scientific variants from the referenced Campaign. It must never copy public publication policy into `ExperimentConfiguration`.

## 1.2 DataPolicy is immutable scientific context

Every draft, manifest, run request, fake receipt, and fake report carries the exact `data_policy_digest` from the Campaign.

The development DataPolicy means, in substance:

```text
candidate skill:
  participant-owned
  public release required for this Climb
  training use prohibited

raw episodes:
  local retention allowed
  server upload prohibited
  public release prohibited
  reproduction access requires consent
  training use prohibited

derived artifacts:
  aggregate scores public
  UpliftReport public
  redacted trace projection public
```

PR6 shows those rights before a draft can be started.

PR8 requires affirmative acknowledgement of the exact digest. A confirmation token alone is not a DataPolicy acknowledgement.

## 1.3 Evaluation backend versus subject runtime

The development Campaign carries:

```yaml
evaluation_backend:
  kind: local_techtree
  attestation: participant
```

Separately, the subject configuration says:

```yaml
runtime:
  type: docker
```

The fake executor does not execute the subject and therefore fake receipts use:

```text
subject_runtime.kind = not_executed
```

The `evaluation_backend` is still copied unchanged because it is part of Campaign lineage.

## 1.4 No live signing

The crypto layer remains inert.

PR6–PR8 must not:

```text
generate a persistent key
write a private key
register an executor identity
sign a receipt
sign a report
pretend a fake run is attested
```

Protocol signature fields remain absent or null according to the frozen models.

## 1.5 No Relay

No file, status, model, dependency, or artifact introduced by these slices may mention or require NeMo Relay.

## 1.6 No packaged placeholder science

PR4A ships an empty embedded catalog and tests a complete synthetic graph through dependency injection.

Until PR12 generates the real `procedure-transfer-dev@1` graph:

```text
techtree climb list
```

may correctly return no packaged Climbs.

PR6 and PR8 integration tests use the complete synthetic catalog fixture. They must not introduce hand-authored placeholder engine, membership, or validation digests into package resources.

- Expiry default is 15 minutes.
- Consumption is idempotently rejected after first success.

## 7.3 Event-journal invariants

- The initial event sequence is `0`.
- Every next event increments by exactly one.
- `events.jsonl` is append-only.
- Each line is one compact JSON object plus `\n`.
- Each append is flushed and fsynced.
- A malformed event is an integrity failure.
- A sequence gap or duplicate is an integrity failure.
- `state.json` is a disposable cache.
- `events.jsonl` is the durable truth.
- Timestamps need not be strictly monotonic; sequence is authoritative.
- The journal contains no secret.
- Heartbeats are not journal events.

### Event semantics

#### `run.created`

```text
sequence: 0
previous_phase: null
phase: created
details:
  request_digest
```

#### `worker.started`

```text
previous_phase: created
phase: created
details:
  worker_pid
```

This is a same-phase informational event.

#### `phase.entered`

```text
previous_phase: prior phase
phase: target phase
details:
  optional label
```

#### `progress.updated`

```text
previous_phase: current phase
phase: current phase
details:
  current
  total
  label
```

#### `cancel.requested`

```text
previous_phase: active phase
phase: cancel_requested
details:
  requested_by
```

#### `run.failed`

```text
previous_phase: any nonterminal phase
phase: failed
details:
  error: CliError
```

#### `run.cancelled`

```text
previous_phase: cancel_requested
phase: cancelled
```

#### `result.written`

```text
previous_phase: building_report
phase: building_report
details:
  result_digest
```

#### `run.completed`

```text
previous_phase: building_report
phase: completed
details:
  result_digest
```

```text

evaluation backend local_techtree

```

### Idempotent start algorithm

1. Generate proposed `run_id`.
2. Acquire draft lock through `DraftStore.claim_start`.
3. If an existing start record is returned:
   - use its `run_id`;
   - do not consume a second token;
   - return existing run status if run exists;
   - if status is `CLAIMED` and run directory is absent, repair by creating it;
   - never allocate a second run.
4. Build immutable `RunRequest`, including `PolicyAcknowledgement`.
5. Create `RunStore`.
6. Stage run-owned inputs.
7. Launch worker.
8. Persist PID and `worker.started`.
9. Mark draft start `LAUNCHED`.
10. Return status.

### Launch failure

If worker launch fails:

```text
run remains addressable
run state becomes failed
draft start becomes launch_failed
confirmation remains consumed
repeated start returns the same failed run
```

Do not create another run automatically. A future explicit retry operation may do so.

# 9. Cross-slice crash-consistency rules

## 9.1 Draft prepare crash

A final draft directory appears only after complete staging and verification.

## 9.2 Start crash before claim

No state changed; user may retry with same token.

## 9.3 Start crash after claim but before run creation

`start.json` contains the canonical run ID.

Retry repairs the same run ID.

## 9.4 Start crash after run creation but before launch

Retry sees existing run and launches only when no worker-start evidence exists.

## 9.5 Launch succeeds but launcher crashes before PID projection

Worker records its own PID as its first action.

Retry returns existing run.

## 9.6 Event append succeeds but state write fails

Next `state()` rebuilds projection from journal.

## 9.7 Result write succeeds but completion event fails

Report exists but run is nonterminal.

A later reconciliation operation may verify report digest and append completion. PR8 tests should at least detect this state; automatic repair may be deferred.
