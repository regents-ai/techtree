# Techtree v0.2 implementation contract

Status: binding plan for implementation  
Audience: product, protocol, CLI, plugin, platform, and release implementers  
Scope: the release after v0.1

## Authority and supersession

This document is the implementation authority for Techtree v0.2. Earlier
plans, decisions, and tickets remain useful context, but they do not create a
parallel v0.2 architecture. Every v0.2 ticket must link to this document and
name exactly one work package.

The v0.1 proof bytes and their verification semantics remain immutable. When
this document conflicts with an older roadmap or unimplemented ticket, this
document governs v0.2. No production work begins from an older ticket until
its scope and acceptance criteria have been reconciled here.

## Release identity

Techtree v0.2 is the execution-provenance and subject-portability release.

It does not introduce Environment Forge, automatic Skill optimization,
held-out optimizer/proving workflows, or model training. Those remain v0.3 or
later.

Public website copy, roadmap copy, tickets, and release notes must use this
release identity. Earlier copy describing Environment Forge as a v0.2 feature
is superseded.

The public summary is:

> v0.2 adds Prime-hosted comparisons, Fabric-backed Hermes and Codex subjects,
> bounded Relay evidence, and provider reruns. Future releases will add
> environment creation, optimization, and training.

## Product outcome

v0.1 proves that a participant can compare one changed Skill under the same
agent, model, tasks, and evaluation settings, then sign and verify the result
offline. In v0.2 the same controlled-comparison protocol becomes portable
across execution locations and subject harnesses without compressing unlike
evidence into one trust label.

A reader must be able to answer these questions independently:

- Are the files and signatures intact?
- Was this a valid controlled comparison?
- Where did it run?
- What participant, provider record, or provider attestation exists?
- What instrumentation profile was requested and observed?
- How strongly was the served model identified?
- Was it rerun or independently reproduced, and with what declared drift?

These are evidence facets, not ranks. Results may be filtered by them, but are
never sorted into a truth or performance leaderboard.

Historical proof compatibility is also a discovery filter, not release
provenance. The `v0.1` selector maps to the frozen
`hello-world-climb@1` publication family because v0.1 proofs did not record a
Techtree product release identifier. It must not be presented as proof of which
CLI or site release created an entry, and it does not rewrite historical bytes.

## Release scope

The stable v0.2 matrix is:

```text
evaluation engine
    exact founder-approved Prime Verifiers build

execution backends
    local
    Prime Hosted Evaluations

subject backends
    direct Hermes, retained for parity
    Hermes through NeMo Fabric
    Codex through NeMo Fabric

operator surfaces
    Hermes
    Codex

evidence backends
    native Verifiers evidence
    optional NeMo Relay evidence
```

NemoClaw, Grok Build, and Pi may be preview integrations but do not block the
release. Environment creation, automatic Skill search, sealed proving splits,
training, a local control-plane dashboard, and broader stable harness support
are v0.3 or later.

## Non-negotiable boundaries

- Verifiers remains authoritative for task identity, task results, and reward.
- A backend or evidence change never silently reinterprets an existing
  Campaign.
- A provider-hosted run is not called an independent reproduction.
- Relay is observe-only and never changes the canonical score.
- No reusable credential, hidden answer, grader source, environment dump,
  private path, raw Episode, or private trace reaches a public proof.
- The model never approves paid inference, publication, reproduction, or data
  release.
- Completed evidence is append-only.
- Automatic duplicate paid submission is forbidden after ambiguous transport.
- v0.1 local proofs continue to verify without rewriting their bytes.

## Four-plane execution model

Every paid run resolves four independent contracts:

1. Evaluation engine — Verifiers supplies task and reward truth.
2. Execution backend — local Techtree or Prime Hosted Evaluations.
3. Subject backend — direct integration, Fabric, or a Verifiers-native harness.
4. Evidence backend — native evidence, optionally supplemented by Relay.

No plane implies another. Prime-hosted does not imply Fabric. Fabric does not
imply Prime-hosted. Relay evidence does not imply provider attestation.

```python
class ResolvedExecutionPlan(ProtocolModel):
    evaluation: EvaluationEngineRef
    execution: ExecutionBackendSpec
    subject: SubjectBackendSpec
    evidence: EvidenceBackendSpec
```

### Campaign and execution-plan ownership

A v0.2 Campaign binds exactly one `ResolvedExecutionPlan` digest. The plan is
not a mutable run-time choice beneath an already frozen Campaign. Selecting a
different execution, subject, or evidence backend creates a different
Campaign.

A Climb may offer several Campaign variants derived from one scientific
template, but every paid run resolves to one immutable Campaign and one
immutable execution plan before approval. Backend parity and provider reruns
compare distinct immutable Campaigns under an explicit compatibility policy;
they never describe different plans as one Campaign.

### Configuration compatibility

One policy model covers provider reruns and backend-parity studies:

```python
class ConfigurationCompatibilityPolicy(ProtocolModel):
    purpose: Literal["reproduction", "backend_parity"]
    source_campaign_digest: Digest
    required_equal_paths: tuple[str, ...]
    allowed_drift_paths: tuple[str, ...]
    comparison_algorithm: Literal["rfc6901_json_pointer_v1"]


class ConfigurationComparison(ProtocolModel):
    policy_digest: Digest
    source_campaign_digest: Digest
    candidate_campaign_digest: Digest
    observed_drift_paths: tuple[str, ...]
    compatibility: Literal[
        "exact_configuration",
        "compatible_with_declared_drift",
        "incompatible",
    ]
```

Paths use RFC 6901 JSON Pointer syntax. Techtree compares materialized
canonical Campaigns, not summaries. Every observed difference must be allowed,
required-equal paths may not differ, and allowed and required-equal paths may
not overlap. Drift paths are sorted and unique before hashing. Any undeclared
change makes the comparison incompatible.

## Evidence contract

Evidence facets remain orthogonal.

```yaml
artifact_integrity:
  status: verified | invalid

comparison_validity:
  status: valid | invalid | indeterminate
  campaign_digest: sha256:...
  mutation_axis: skill
  declared_difference_digest: sha256:...
  observed_difference_digest: sha256:...
  reason_codes: []

execution_location:
  kind: local | prime_hosted

execution_observation:
  participant_attestation:
    status: verified | invalid | absent
    key_fingerprint: null | "..."
  provider_record:
    status: absent | participant_captured | publication_service_retrieved
    provider: null | prime
    provider_run_ref: null | "..."
    record_digest: null | sha256:...
  provider_attestation:
    status: absent | verified | invalid
    attestation_digest: null | sha256:...

trace_coverage:
  kind: not_requested | unavailable | incomplete | complete_for_profile
  coverage_profile_digest: null | sha256:...
  reasons: []

model_identity:
  pin_strength: mutable_alias | provider_revision | artifact_digest

reproductions:
  - proof_digest: sha256:...
    kind: same_participant_provider_rerun | independent_reproduction
    compatibility: exact_configuration | compatible_with_declared_drift | incompatible
    executor_fingerprint: "..."
```

An uplift may be the headline only when artifact integrity is verified and
comparison validity is valid. Invalid or indeterminate comparisons may be
published as failure evidence, but are not presented or ranked as uplift.

`participant_captured` means a Prime run reference was copied into the
participant-signed bundle. It is rendered as “Prime run reference captured,”
never “Prime verified this run.” The latter requires an independently retrieved
provider record or a verifiable provider attestation.

`not_requested` means the Campaign selected native-only evidence.
`unavailable` means Relay was requested but produced no usable evidence.
Use “provider-hosted rerun” for a same-participant run on Prime; it is not an
independent reproduction.

### Evidence availability and proof closure

Every digest referenced by a proof says where its bytes exist and what an
offline verifier can prove:

```python
class EvidenceArtifactRef(ProtocolModel):
    digest: Digest
    media_type: str
    size_bytes: int
    availability: Literal[
        "embedded_in_proof",
        "private_local_archive",
        "provider_retrievable",
        "not_retained",
    ]
    verification: Literal[
        "recomputable_from_bundle",
        "verified_during_run_and_receipted",
        "commitment_only",
    ]
```

A missing blob is never silently treated as verified. A public verifier may
verify a signed commitment to private evidence without claiming it rechecked
the private bytes.

## Skill projection

Hermes and Codex may discover the same source Skill differently. Projection
evidence records this rather than claiming equivalent harnesses.

```python
class SkillProjectionSpec(ProtocolModel):
    source_skill_tree_digest: Digest | None
    projection_policy_digest: Digest
    subject_backend_digest: Digest
    projection_kind: str
    included_paths: tuple[str, ...]
    destination_root: str
    collision_policy: Literal["fail", "replace"]
    transformations: tuple[str, ...]
```

`None` is the intentionally empty tested-Skill set. Baseline and candidate use
the same projection-policy digest; only the declared Skill source may differ.
An empty baseline has no realized or transformed files and must discover no
tested Skill.

## Upstream adoption and freeze

WP0 records exact Verifiers, Prime client/API, Fabric runtime and adapters, and
Relay/ATOF/ATIF coordinates in `docs/v0.2/UPSTREAM_CONTRACT_LOCK.json`.

Once that lock is committed, the adopted candidates are frozen for the v0.2
release line. Discovering a newer build is not authority to upgrade it. A
replacement requires a new explicit founder decision, lock revision, affected
fixture regeneration, and rerunning every affected conformance work package.

The v0.1 EngineLock remains historical and unchanged.

### Contract spikes before production code

One disposable conformance environment captures the real supported contracts
before an adapter or remote backend is implemented.

The Prime spike records sanitized fixtures for create, get, list, samples,
logs, stop, and terminal failure; exact client/API and environment versions;
evaluation, suite, and run identifiers; status vocabulary; pagination; result
availability; cancellation; billing-principal representation; artifact access;
and any provider idempotency guarantee. It proves how an exact environment
version is selected and separately tests whether Fabric-backed custom harnesses
are supported. Nothing relies on `latest`.

Until provider idempotency is proven, Techtree describes only local intent
deduplication. Any path using `prime eval` forces `--skip-upload`, and a contract
test fails if the flag disappears. Hosted secret values never enter arguments,
persisted intents, logs, or proofs; only provider-owned secret references or a
native credential store may cross the boundary.

The Fabric spike captures runtime/schema versions, adapter package and contract
coordinates, descriptors, discovery provenance, requirements, and real
capability gaps. The Relay spike captures package, ATOF, ATIF, configuration,
delivery, teardown, and coverage contracts. Sanitized fixtures go under the
owning component's tests; credentials and private traces never do.

## Fabric admission and subject execution

Fabric follows this order:

```text
requirements → Fabric plan → Techtree admission → Fabric Doctor
→ human approval → fresh runtime → invoke → stop and collect
```

The plan receipt binds Fabric and adapter versions, descriptor and discovery
provenance, harness identity, executable/source digest, requested and admitted
requirements, and all projection digests. Unsupported behavior fails admission
before spend.

```yaml
FabricPlanReceipt:
  fabric_package_version:
  fabric_schema_version:
  adapter_id:
  adapter_package_version:
  adapter_contract_version:
  descriptor_digest:
  discovery_provenance:
  harness_name:
  harness_version:
  executable_or_source_digest:
  requested_requirements: []
  accepted_requirements: []
  unsupported_requirements: []
  missing_runtime_requirements: []
  agent_config_digest:
  skill_projection_spec_digest:
  mcp_projection_digest:
  model_projection_digest:
  admitted: true | false
  reasons: []

SubjectExecutionReceipt:
  plan_digest:
  runtime_id:
  invocation_id:
  request_id:
  terminal_status:
  result_digest:
  artifact_manifest_digest:
  usage_digest:
  failure_class:
  cleanup_status:
```

Baseline and candidate run in fresh runtimes derived from the same admitted
plan except for the declared Skill mutation. Codex Campaigns requiring
unsupported normalized tool controls fail before spend; unsupported behavior
is never silently dropped.

Fabric-Hermes parity uses two immutable Campaigns whose only differences are
permitted by a backend-parity policy. Parity covers task membership, model
coordinate, Skill bytes, model requests, tool calls and results, reward
aggregation, terminal classification, cleanup, and proof semantics.

## Relay evidence

Relay is optional, observe-only evidence. Each released adapter has an exact
coverage profile. `complete_for_profile` is calculated, never manually
asserted.

```yaml
coverage:
  calculation_version: relay-coverage-v1
  expectation_source:
    - verifiers_trace
    - fabric_execution_receipt
    - native_harness_events
  expected_event_ids: []
  observed_event_ids: []
  missing_event_ids: []
  unexpected_event_ids: []
  unmatched_events: []
  status: complete_for_profile | incomplete | unavailable
  reasons: []
```

Complete coverage requires registration before subject start, an opened and
closed root scope, correlation of every required event from declared
expectation sources, no missing required event, no dropped-event diagnostic,
successful flush and shutdown, and pinned profile and calculation versions.

A deterministic Relay-off/Relay-on fixture requires exact equality for task
identities, model request payloads, tool calls and results, rewards,
aggregation, and terminal classification. Only evidence artifacts may differ.

Relay teardown is ordered: await the subject result, confirm quiescence when
available, close the root scope, force-flush ATOF subscribers, clear and shut
down Relay, inspect plugin and delivery diagnostics, hash ATOF, derive or
collect ATIF, validate correlations, then write the evidence statement.
Successful flush alone never establishes durable or lossless delivery.

## Paid remote execution

### Estimate and approval

No remote create request is sent without a valid unexpired approval:

```yaml
RemoteExecutionEstimate:
  execution_plan_digest: sha256:...
  provider: prime
  billing_principal_label: "..."
  currency: USD
  estimated_cost: null | "..."
  maximum_authorized_cost: "..."
  estimate_source:
  uncertainty_disclosure:
  expires_at:

ExecutionApproval:
  execution_plan_digest: sha256:...
  estimate_digest: sha256:...
  maximum_authorized_cost: "..."
  billing_principal_label: "..."
  approved_at:
  approval_method:
```

Approval binds the exact plan, maximum spend, and non-secret billing-principal
label. Any plan, provider, model, task count, budget, or account change
invalidates it. The estimate states whether one ceiling covers both arms or
each arm has a separate ceiling.

### Hosted comparison topology

The Prime contract spike determines whether the comparison uses one evaluation
with multiple suites/runs or two evaluation IDs. Techtree represents the real
provider shape without pretending there is one remote ID:

```yaml
HostedComparisonExecution:
  comparison_id:
  execution_plan_digest:
  baseline:
    prime_execution_receipt_digest:
  candidate:
    prime_execution_receipt_digest:
  pairing:
    ordered_membership_digest:
    task_pairing_digest:
    arm_ordering:
    completeness:
```

Both arms must resolve to the required exact environment version, have equal
ordered task identities, pair every task result, and contain only drift allowed
by the compatibility policy.

### State and recovery

The five durable user states are `prepared`, `running`, `completed`, `failed`,
and `cancelled`. Provider provisioning, queue position, episode progress,
Relay flush, collection, publication, and withdrawal are append-only events.
Orthogonal remote control records submitting, identified,
reconciliation-required, and terminal conditions.

```yaml
remote_control:
  status: none | submitting | identified | reconciliation_required | terminal
  provider_run_ref:
  last_observed_provider_status:
  last_checked_at:
  ambiguous_submission: true | false
```

A request that may have been accepted but lost its response stays running and
requires reconciliation. Techtree never automatically resubmits after an
ambiguous paid transport failure unless the upstream idempotency guarantee was
proven and locked. Recovery tests cover estimate expiry, plan change after
approval, baseline-only creation, one terminal arm with ambiguous second-arm
submission, provider ID not persisted, collection interruption, and
cancellation interruption.

### Provider response handling

For every response:

1. Enforce size and redirect policy.
2. Hash received transport bytes in memory.
3. Parse with a bounded schema.
4. Remove or reject forbidden secret-bearing fields.
5. Canonicalize and persist only the sanitized provider record.
6. Record a transport digest when safe as a commitment and a sanitized-record
   digest whose bytes are persisted.
7. Never persist raw bytes containing forbidden secret material.

`PrimeExecutionReceipt` therefore carries
`provider_transport_digest` and `provider_sanitized_record_digest`, not one
ambiguous provider-record digest.

It also binds the exact Prime client/API, evaluation/environment/version,
suite/run IDs, request digest, terminal status, samples manifest, diagnostic
logs, retrieved artifact references, collection completeness, non-secret
billing-principal label, and cancellation timestamps. A provider-attestation
digest remains absent until a real Prime-verifiable assertion exists. Logs are
diagnostic evidence, never score truth.

## Operator contract

Hermes and Codex use the same machine-readable Techtree surface to inspect
setup and supported backends; list Climbs; prepare a comparison; present cost,
evidence, and credential ownership without secrets; request native human
approval; start, watch, cancel, and inspect a Result; verify a proof; and offer
publication and a provider-hosted rerun.

Operator integrations own no scientific state, scheduler, receipt, approval,
or publication rule. Preview integrations may wrap this same surface but do not
expand the stable release matrix.

## Publication-service dependency

v0.2 extends the existing publication protocol; it does not invent a second
one. The inherited v0.1 contract is defined by
[`0038-public-run-log.md`](../../cli/docs/decisions/0038-public-run-log.md),
[`publication/models.py`](../../cli/src/techtree/publication/models.py), and the
platform's publication ingestion under `platform/lib/techtree/network/`.

That contract already supplies bounded proof ingestion, verification,
idempotence by proof digest, a server-signed `PublicationReceipt`, signed
withdrawal, replay-safe append-only tombstones, and private raw Episodes and
Traces. WP5 extends the proof and public projection for v0.2 evidence facets;
it does not weaken or duplicate these behaviors.

## v0.1 compatibility

Every frozen v0.1 proof fixture remains byte-for-byte unchanged and verifies
under the v0.2 CLI with the same normalized verification outcome and claim
semantics. Human presentation text need not be byte-identical unless it is part
of a frozen golden fixture.

Historical v0.1 artifacts are read through versioned read-only projectors.
Their source bytes and digests are never rewritten and old shapes never return
to live write paths.

## Security and data boundary

- Hermes, Codex, Prime, and model-provider credentials remain owned by their
  native host or provider client.
- OAuth tokens, API keys, refresh tokens, environment dumps, and reusable
  credentials are forbidden in inputs, receipts, proofs, traces, publication
  payloads, logs, and errors.
- Plugins receive capability outcomes and non-secret account labels, never
  secret material.
- Remote responses and artifacts are size-bounded, content-addressed, and
  verified before parsing.
- Redirects are refused unless a future signed contract binds the destination.
- Hidden answers and grader implementation never enter an operator context,
  public trace, or future optimizer.
- Publishing remains an explicit human-approved act; no run publishes itself.

## Interruption matrix

Every remote ticket specifies the durable state, next safe operation, whether
spend may continue, forbidden automatic retries, evidence that may still be
issued, and permitted public label for its applicable boundaries.

```text
Prime
  before request construction
  estimate expired or plan changed after approval
  intent persisted, before send
  request sent, response not received
  response received, provider ID not persisted
  baseline created, candidate not created
  first arm terminal, second-arm submission ambiguous
  provider ID persisted, polling not started
  during logs or sample collection
  during cancellation
  terminal remotely, collection incomplete

Fabric
  plan succeeds, Doctor fails
  runtime partially starts
  invoke transport fails
  target returns malformed result
  target completes, collection fails
  stop fails
  worker is hard-killed

Relay
  plugin registers late
  root scope never opens or closes
  ATOF flush fails
  ATIF serialization fails
  sink fails or events/spans drop
  process dies before teardown

Publication
  proof accepted, receipt response lost
  duplicate publication request
  withdrawal response lost
```

## Release verification

The v0.2 release gate requires:

- clean local direct-Hermes and Fabric-Hermes parity comparisons;
- one Fabric-Codex within-harness comparison;
- Relay not-requested, complete, incomplete, and unavailable proofs;
- one Prime-hosted two-arm comparison using provider-fetched results;
- one ambiguous submission reconciled without duplicate spend;
- one provider-hosted rerun with declared drift;
- local offline verification of every proof;
- staged publication, idempotence, withdrawal, evidence-filter browser checks;
- fresh-session Doctor checks for Hermes and Codex;
- a credential canary proving no reusable secret reaches persisted or public
  bytes; and
- unchanged v0.1 fixtures verifying with the same normalized outcomes and
  claim semantics.

Every remote ticket covers its happy path, tampering, interruption,
cancellation, timeouts, idempotency, and secret scrubbing. The dispatch order
and ticket mapping live in [`../v0.2/TICKETS.md`](../v0.2/TICKETS.md).

The highest-leverage prerequisite is one tiny exact deterministic Prime
conformance environment. It must support a local run, hosted run,
provider-hosted rerun, Fabric-Hermes run, Relay-complete run, and deliberately
incomplete Relay run. It tests infrastructure conformance and creates no public
performance claim.

Before editing production code, an implementer reads this plan and the v0.1
decisions governing Campaigns, runs, receipts, proof, publication, credentials,
and cancellation; claims the owning Bead; completes the applicable contract
spike; commits lock/decision changes before backend code; and implements only
the current work package's first executable caller.

## Later releases

v0.3 may add Environment Forge, a development/proving split, external Skill
optimization, ImprovementPrograms, training handoff, a local control-plane
dashboard, and a broader certified harness matrix. The optimizer never sees
hidden proving answers and never approves its own paid proving run.

Independent reproduction networks, hardware attestations, on-chain anchoring,
identity verification, marketplaces, incentives, leaderboards, always-on
mobile orchestration, and public raw traces remain discovery work without a
promised release.
