## Item 4: reliable installation and release preparation

What exists: `cli/pyproject.toml` `[build-system] requires = ["hatchling"]`
is unpinned; the dev group pins `hatchling>=1.27,<2` and `cli/uv.lock`
resolves it to 1.32.0, while an isolated `uv build` resolves the newest
release (1.32.4 today). That difference made the first 0.2.1 wheel
irreproducible (WHEEL/RECORD only). `cli/release/release-inputs.json` says
minimum and maximum-tested host Hermes are both `0.20.1`; 0.2.1 was qualified
on 0.21.3 (upstream `6d712cf8`). `forge run` already refuses a missing or
signed-out `techtree` profile with the exact command to run
(`forge/profile.py`); `techtree doctor` only reports whether the profile
directory exists.

Changes:

1. Pin the build backend to one exact version in `[build-system]` and the
   dev group (`hatchling==1.32.4`); `uv lock` so the lock agrees. The plugin
   has no build backend and needs nothing.
2. Add `cli/tools/build_release_wheel.sh`: given a commit, builds the wheel
   from a clean detached checkout of that commit into a chosen directory and
   prints the SHA-256, so the approved wheel is never built from a working
   tree again. The release procedure in the handoff points at it.
3. Reconcile the Hermes values: `maximum_tested_host_hermes_version` becomes
   `0.21.3`; the minimum becomes what decision 4 says. `make regenerate`
   rebuilds the release core and the bootstrap minimums follow.
4. `techtree doctor` reports the `techtree` profile's sign-in the way
   `forge run` checks it (Hermes is asked `auth status`, read-only; the
   auth store is never opened), for the provider the person names or, when
   none, for each provider Hermes lists as configured. Missing or signed out
   is a warning that names the command; the doctor payload carries the
   same `forge_profile_missing` / `forge_profile_signed_out` codes so an
   agent reading JSON can act.

Acceptance: two wheels built from the same commit on this Mac and in CI
(the publish workflow's `uv build --wheel`) have the same SHA-256; the
release inputs, release core, bootstrap and `techtree release verify` agree
on the Hermes versions; `techtree doctor` on this Mac shows the `techtree`
profile signed in to `openai-codex`, and shows the warning with the exact
command on a throwaway `HERMES_HOME` with no profile. Gates: `make check`,
`make check-plugin`, `mix test`.

Needs the founder's word: nothing until release.

## Item 2: task selection and qualification feedback

What exists: `forge/qualify.py` records six named checks per task
(`image_build`, `workspace_at_base_commit`, `verifier_material_absent`,
`tests_recognized`, `control_fails`, `reference_passes`) and
`forge status` prints `task: not qualified` with the failed check names and
their raw detail. The generator's skipped candidates are printed as reason
counts. A build with zero usable tasks fails with `forge_no_usable_tasks`.
Nothing says, in plain words, why a task was rejected or whether the
surviving set is enough for a comparison.

Changes:

1. After `forge build` and in `forge status`, one plain sentence per task:
   "qualified" or the first failed check in a person's words (for example
   "rejected: the unrepaired code already passes 2 of its 3 fail-to-pass
   tests", "rejected: the reference repair did not make the tests pass",
   "rejected: the task image did not build"). The raw check detail stays
   available under `--json`; the words live in one table in
   `cli/commands/forge.py`, next to `OUTCOME_WORDS`.
2. A summary line: N emitted, K qualified, M candidate commits skipped, with
   the top skip reasons in plain words.
3. A warning `forge_few_tasks` when fewer than three tasks qualified: one or
   two tasks give a comparison that can only say "this attempt", not "this
   Skill". The warning is in the JSON envelope and the human output; the
   build is still usable (a person may want exactly one task).
4. Qualify three varied public repositories for real, with Docker and no
   model: the existing `click` build, one more Python repository, and one
   Node, Go or Rust repository. Evidence (build records, qualification
   records, skip reasons, the plain-language output) goes to
   `artifacts/techtree-pairing/release-v022/Q-*`. Cost USD 0. If a language
   yields no usable task, that is a finding recorded in the changelog, not
   a reason to hide the language.

Acceptance: on the three real builds the output reads correctly to a person
who has never seen the check names; a rejected task's reason matches its
recorded check; the warning appears on a build with fewer than three
qualified tasks and not otherwise. No schema change; no new tests unless
directed.

Needs the founder's word: nothing (Docker runs, no provider calls).

## Item 3: decision-grade reports

What exists: `forge/compare.py` pairs every task × repetition, counts wins,
losses, ties and unresolved, computes a mean delta, and says "Partial" until
every planned pair has a verdict on both sides. `forge/report.py` renders
the totals, the pair table, patches and grading, allowed differences and
limits. A comparison with more wins than losses reads as a success even if
one task regressed; there is no per-task view across repetitions; there is
no explicit "inconclusive".

Changes (canonical shape, hard cutover; the comparison schema version moves
to `v1alpha3` and existing comparison records on disk are re-read only by
the new shape):

1. A `verdict` on the comparison record with exactly these values and rules,
   applied in this order:
   - `inconclusive`: any planned pair is unresolved, or fewer than three
     pairs were graded;
   - `mixed`: at least one win and at least one loss;
   - `improved`: at least one win, no losses;
   - `regressed`: at least one loss, no wins;
   - `no_difference`: every graded pair tied.
   The summary sentence leads with the verdict in words.
2. A `regressions` list: every task with at least one lost pair, with the
   attempts lost and won. On the page it is its own section above the totals
   ("Where the Skill lost"), shown even when the mean delta is positive.
3. Per-task consistency: for each task, wins / losses / ties across its
   repetitions, and a flag when the same task went both ways. On the page
   this is a column in the task table and a sentence in "In short" when any
   task is inconsistent. With one repetition the section says so plainly:
   "one attempt per task; consistency across attempts was not measured".
4. `forge compare` and `uplift start` terminal output and the plugin-facing
   JSON carry the verdict, the regressions and the consistency, so an agent
   reads the same three facts a person sees.

Acceptance: the existing real comparison in
`artifacts/techtree-pairing/release-v020/I1c-qualified-r3/home`
(one task, one repetition, tie) re-renders as `inconclusive` with the
one-attempt sentence; a synthetic record with a positive mean and one lost
task shows the regression section and reads `mixed`. Copy guard
`test_release_copy.py` stays green. Existing unit tests in
`tests/unit/test_forge_compare.py` are updated to the canonical shape
(rule 7); no new test files unless directed.

Needs the founder's word: nothing.

## Item 1: guided "evaluate this Skill on my repository" flow

**Deferred by the 2026-09-22 founder scope amendment above.** The material in
this section remains implementation history, not 0.2.2 release acceptance.

What exists: `forge build`, `forge run` (baseline and candidate), `forge
compare` and `uplift` each preview and ask individually; `review_run_spec`
already states what leaves the machine and the limits. There is no single
entry point, and the Hermes plugin has no forge tools at all (its 17 tools
cover bootstrap, climb, run, proof, publish and uplift).

Changes:

1. `techtree forge evaluate --repository PATH --skill PATH --provider P
   --model M [--repetitions N] [--language L]`. One walk-through:
   prerequisites (Docker, Hermes, the `techtree` profile signed in to P,
   using item 4's check) → build and qualify (item 2's output) → one
   consolidated preview stating what leaves the machine (model calls to P
   on the person's own sign-in; nothing else), what stays local (the
   repository, the tasks, every patch and verdict), what will run (tasks ×
   repetitions × two arms, time limits, container limits) → one approval →
   baseline arm → candidate arm → compare → the verdict, the regressions and
   the report path (item 3). Every intermediate id is printed as it is
   created, so an interrupted walk-through leaves ordinary `forge status`
   evidence and can be continued by hand with the existing commands; the
   walk-through itself does not resume.
2. `--json` returns the same NextAction chain the individual commands use:
   after the preview it returns `approval_required` with the plan digest;
   with `--yes` it runs to the end and returns the comparison status.
3. Docs: `cli/docs/product-architecture.md` forge paragraphs, README "What
   you can use today", `platform/priv/changelog.md` and the root
   `CHANGELOG.md` (identical bytes), the site `/start` and `/docs` copy
   where they describe the experiment. Customer copy carries no
   implementation words.
4. Hermes plugin: per decision 6. The recommended shape is two read-only
   tools (`techtree_forge_status`, `techtree_forge_report`) plus operator
   Skill text that tells the agent to run `techtree forge evaluate` in the
   person's terminal and read the result back, because a multi-hour
   experiment does not belong inside one tool call.

Acceptance: on this Mac, `techtree forge evaluate` on the `click` repository
with the `sentinel-copy` Skill runs end to end on the `techtree` profile
with `openai-codex` / `gpt-5.6-sol` and ends with a verdict and a report
(announced before the first run; expected cost USD 0, under the USD 10
cap); a second walk-through on a fresh Linux worker from the 0.2.2 wheel
does the same. Interrupting a walk-through mid-run leaves a run that
`forge status` reads back. Gates as in item 4.

Needs the founder's word: the real evaluation runs are on the granted cap;
the first run of the new kind is announced first. The Linux worker is a
destroyed-after-use Fly machine as for 0.2.1 (say the word before it is
created).
