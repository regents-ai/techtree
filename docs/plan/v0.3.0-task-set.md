## 2. Definition of done for the whole release

0.3.0 is done when every line below is true on one exact release-candidate
revision, and each line has evidence under
`artifacts/techtree-pairing/release-v030/`:

1. **One boundary, two producers.** A Repo2RLEnv repository build and a
   Skill2Env Skill build both write the same committed task-package shape
   (`TaskContentManifest` + `TaskSetCommitment`, build schema `v1alpha3`),
   with typed provenance and no fabricated Git facts on the Skill side.
   Qualification evidence sits beside the committed tree and references its
   content digest; it is never part of the bytes it verifies. (U2, R20, R28)
2. **Offline, pinned, credential-free builds.** Every generated or imported
   image recipe builds with networking disabled from digest-pinned base
   images that the release-controlled bootstrap acquired beforehand, from a
   bounded context that is exactly the task's `environment/` directory. A
   recipe that fetches, uses a remote context or frontend, or needs a
   credential fails before qualification, with the reason retained. (R30,
   KTD6)
3. **Common qualification on exact bytes.** For both producers: the package
   re-hashes to its commitment; hidden verifier and reference material is
   absent from every subject-visible input and from the subject image; the
   no-op fails; the reference passes; output limits hold. Failures retain
   evidence and reject the task; they never rewrite bytes. (R29, R30)
4. **Old records refuse plainly.** A pre-cut alpha build, qualification or
   comparison record on disk stays untouched and returns the named
   unsupported-schema error with its path; there is no legacy reader, alias,
   fallback parse or dual output. (plan "Dependencies and Risks")
5. **Source inspection is inert and honest.** Techtree inventories every
   Source Skill file without executing it, names each admitted, unsupported
   or required file, and blocks before any model call when a required file is
   unsupported. A reduced derivative gets a new source identity with lineage.
   (R15-R17)
6. **Three approvals, one acceptance, no hidden retry.** Planning approval
   binds source digest, recipe, provider/model, disclosed files, egress,
   capabilities and limits before the first model sees Skill content;
   construction approval binds one exact reviewed proposal; collection
   acceptance freezes exact qualified membership; evaluation approval is
   separate and optional. Every change to an input creates a new digest and
   invalidates the stale approval. Every attempt, including failed,
   interrupted and outcome-unknown, is retained and visible; a retry is a new
   linked attempt under a new approval. (R21-R27, R33-R34, KTD5)
7. **Useful without comparison.** A frozen environment runs one baseline
   with no candidate Skill and produces outcomes, captured outputs, failures,
   limits and a plain-language local report with no uplift verdict. Optional
   comparison keeps the 0.2.2 verdict rules and distinct Source, baseline and
   candidate Skill roles and digests. (R4, R19, R35-R37)
8. **Outputs captured before grading.** A bounded manifest of additions,
   modifications and deletions with type, size and digest is written right
   after subject execution; escaping symlinks, missing required outputs and
   incomplete capture are explicit failures. (R38)
9. **Verification from bytes; export private by default.** Creator-side
   verification recomputes every commitment from retained bytes. The default
   export carries the runnable collection, qualification records, provenance
   digests, attribution, limitations and rerun instructions, omits Source
   Skill bytes and authoring transcripts, and its verifier says which
   commitments were recomputed and which are provenance-only. (R39-R42)
10. **`/start` is one copyable instruction.** The public page presents one
    plain-language instruction for a local coding agent, keeps direct CLI and
    Hermes setup as secondary detail, derives install coordinates from the
    verified release payload, and holds no upload, account, bridge, state or
    approval authority. No implementation words in the copy. (R5, R10-R14)
11. **Outside creator and outside evaluator.** The R6-approved outside creator
    completes source review, planning, construction, qualification and
    acceptance on the release candidate without Techtree source changes; a
    different person verifies the sanctioned export and completes one
    baseline on a fresh supported worker. A tie, regression or baseline-only
    result passes. (R43-R45)
12. **Truthful release surfaces.** Version files, both changelogs (identical
    bytes), package metadata, release core, bootstrap, catalog, plugin core,
    README, architecture doc and site copy describe the same proven product;
    the release notes report the deferred 0.2.2 item 1, yield and rejected
    tasks, attempts and interruptions, outside completion time and support
    interventions, unpriced provider usage and every missing verification.
    (R1, R46)
13. **Gates green on the candidate.** `make check`, `make test-integration`,
    `make check-plugin` from `cli/`; platform `mix test` and format check;
    reproducible wheel via `cli/tools/build_release_wheel.sh`; fresh-install
    CLI and plugin checks; browser pass on `/start` at desktop and 320px.
14. **Nothing protected happened without its word.** No push, tag, PyPI
    dispatch, deploy, catalog activation, GitHub release, model run, fresh
    worker or database action occurred except under the founder's explicit
    word for that exact step, recorded in the notes.

Not done, by design (plan "Deferred" and "Outside This Release's Identity"):
private hosting, managed creation, more recipes, arbitrary Skill assets,
live-network tasks, rubric scoring, automatic improvement, marketplace,
payments, any claim of generalization or positive Skill benefit.

### T2. U2b2: base-image acquisition and the network-disabled build (**review**)

- **Objective:** Let a Skill build's `environment/Dockerfile` become an image

  digest-pinned base images named by the recipe (and only those, only from

  fails with the reason retained and no partial image tagged as usable.

  `image_build` check. Every task image of both producers now builds with
  the network disabled (R30 common rule); T4's click rebuild proves the
  repository side. Until T3, a Skill import ends at the `content` phase
  with the receipt `unfinished`: the build record exists, nothing is
  qualified, and status says so.

### T3. U2b3: common qualification of the imported package (**review**)

- **Objective:** Run the common qualification profile (KTD8) on a Skill
  build: package re-hashes to its commitment; subject-visible inputs
  (instruction, `environment/`, the built subject image) contain no byte of
  `tests/` or `solution/`; `solution/solve.sh` then `tests/test.sh` yields
  reward 1 in the isolated runtime; a no-op run yields reward 0; verifier
  output and artifacts stay within limits. Write
  `qualification.json` (`v1alpha2` shape extended only where the Skill
  branch needs a check the repository branch does not have, as a typed
  branch, not an optional field) beside the build.
- **Design points:** The Skill branch of `forge/qualify.py` replaces the
  `require_repository_source("Repository qualification")` guard with a
  dispatch on `source.kind`; checks shared with the repository branch are
  shared code. The runtime that executes `solve.sh` and `test.sh` is the
  isolated task runtime (no network, no credential mounts, bounded time from
  the pinned `task.toml`), not the upstream launcher.
  Shape chosen: `TaskQualification` became a discriminated union by `kind`
  (`RepositoryTaskQualification` keeps the commit and test-name facts;
  `SkillTaskQualification` has none), so every task entry now carries
  `kind` and the record's schema moved to
  `techtree.forge-qualification.v1alpha3` (T4 later gave the build,
  progress and qualification records one schema check, so a pre-cut record
  of any of the three returns `forge_schema_unsupported` with its file).
  The Skill checks in order:
  `hidden_material_private` (host-side: no `tests/` or `solution/` file's
  bytes inside `instruction.md` or any `environment/` file), `image_build`,
  `verifier_material_absent`, `no_op_fails` (reward exactly 0),
  `reference_solution_passes` (reward exactly 1), `verifier_output_bounded`
  (regular files only, no link of any kind, anything unreadable fails,
  1 MiB and 1024 entries across both runs). The reference run starts one
  container and runs `solve.sh` in it by `docker exec` under the pinned
  agent time, then `test.sh` under the verifier time, each deadline kept
  from the host (+10 s for `docker exec` itself), because the image is the
  task author's and nothing inside it can be trusted to keep time (a first
  version used the image's `timeout`, which the review showed a recipe or
  `solve.sh` can replace); a step still running at its deadline ends with
  the container removed, leaves no verdict and says which step it was; a
  `solve.sh` that exits non-zero (the tests then do not run) and an image
  that cannot be started are each rejected in their own words, not as a
  crash of the whole import. Why a run left no verdict is a host-set field
  of the verdict, not a key the tests' `reward-details.json` could forge
  (this also fixes the repository run's "verifier timed out" label).
  Command output is read as UTF-8 with bad bytes replaced (one stray byte
  used to crash the import), and a command stopped at its deadline keeps
  the end of what it printed in `container.log`. The no-op run's bound is
  the verifier time. Progress moved to `techtree.forge-progress.v1alpha3`
  because its completed task entries carry `kind`. The
  import now ends at `completed` and, like a repository build, raises
  `forge_no_usable_tasks` when nothing qualified, with the verdict words.
  `metadata.base_image_pins`, when present, must equal the recipe's `FROM`
  pins (admission). The host-side hidden-material check stays Skill-only
  (T4 decision, below).
- **Known limits carried forward (second review, 2026-09-22):** every forge
  container command's output is held in memory in full, and `/logs/verifier`
  is a host directory measured only after the run, so a hostile task could
  use up the host's memory or disk before its deadline. This is true of every
  forge container run (repository builds and agent grading too), not only
  the Skill import, and 0.3.0 imports only Regents-owned Skills (decision
  1), so it is left for the release that opens imports to outside creators:
  a byte cap on captured output and a size-capped verifier mount. A
  container whose removal fails (the daemon itself failing) is recorded in
  `container.log` but does not by itself reject the task.
- **Exclusions:** Recipe-specific checks (alternative-valid, intentionally
  invalid), collection acceptance, runs, export.
- **Done:** The synthetic task qualifies; each of these rejects with
  retained evidence: no-op passes, reference fails, a `tests/` byte planted
  in `environment/`, a changed package byte, a `solve.sh` that exceeds its
  time; `forge status` reads the verdicts in the item 2 wording; `make check`
  and `make test-integration` green; one local commit.
- **Founder word:** none.
