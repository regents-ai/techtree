# Techtree handoff, 2026-09-19

Written the day after v0.2.0 shipped. This is the single document a new
engineer or agent should read before touching Techtree: what the stack actually
is, what is live right now with its exact coordinates, what v0.2.x and v0.3.0
are meant to contain, and how the EvoSkill v2 codebase relates to that work.

Binding sources, in order of authority: `cli/docs/decisions/` (rulings),
`docs/v0.2/DECISION_LEDGER.md`, `docs/plan/*.md`, then this document. When this
document and a decision disagree, the decision wins.

Standing rules that stay in force for whoever works here next: every push,
merge to `main`, deploy, production data change, Fly secret or config change,
and contract or money action needs the founder's explicit word for that exact
action; hard cutover always (no fallbacks, compatibility branches, shims,
aliases or dual shapes); one writer per repository; never read `.env` files;
never print secrets or connection strings; never drop or recreate a database
without an explicit grant; never write tests unless directed; never run
bd/beads; never bare `git stash`; never `rm -rf`.

### What a person can do today

- Install the CLI from PyPI (`uv tool install --python 3.12 techtree==0.2.0`)
  and the Hermes plugin by commit; `techtree doctor` and
  `hermes plugins doctor techtree --ci` both pass on a clean machine.
- Run the public climb: the same pinned Hermes runs the same synthetic tasks
  twice, once with a declared Skill added, and a signed receipt records the
  difference. `techtree proof verify` checks that receipt offline.
- Publish the result to techtree.sh and browse Results by harness, model,
  exact agent version and exact challenge (an unknown selection shows nothing
  rather than unrelated results). The agent-version browser
  (`docs/plan/agent-version-browsing.md`; the "awaiting founder review" status
  line in that file is stale, the control is on the live `/results` page) groups
  submissions by agent family, defaults to the newest version with accepted
  submissions, keeps the selection in the URL, and never pools scores across
  versions or models. Results and objects from before v0.2.0 remain at their
  addresses; uploads made with CLI 0.1.1 against the earlier campaign are
  refused.
- Improve a Skill with `techtree uplift`: the plugin gathers the context of a
  finished run, proposes a revision, and starts the next measured run.
- Turn a local Git repository into repair tasks with `techtree forge build`.
  Each accepted task is proven both ways (the unrepaired code fails the
  relevant tests, the reference repair passes them) without calling a model,
  and `techtree forge status` shows retained builds, including failed or
  cancelled ones, honestly. Qualification was reproduced for one selected
  public repair, locally and on a fresh Linux worker.
- Read `/changelog`, `/docs`, `/start`, `/verify`, `/blog`, `/repo2rlenv`,
  `/skill.md`, and the machine surfaces
  `/api/v1/{healthz,bootstrap,catalog,climbs/:slug,objects/:digest,publications,publication-keys/:id}`.

### What is deliberately not live

`forge run`, `forge compare`, evaluation of the default or a named Hermes

collaboration and payments, automatic Skill optimization, private proving, and
training. The changelog's "Not in this release" section is the customer-facing
statement of this list; keep it truthful.

## 3. v0.2.x: what we know we want

The order below is the recommended order, not a promise. Each item is
released only when it is qualified end to end, and the changelog says exactly
what was and was not exercised.

### 3.1 `forge run` and `forge compare` (the Repo2RLEnv local lane)

Plan: `docs/plan/repo2rlenv-local-lane.md`. The target workflow: a person
points Techtree at a repository on their own machine, Techtree builds proven
repair tasks (already live), then runs the person's own Hermes against those
tasks twice, as configured today and with a candidate Skill added. The
difference is private local evidence about whether the Skill helps that agent
on that codebase, and it feeds the existing `uplift` loop.

Facts the design rests on: forge artifacts stay local unless separately
approved for disclosure; the subject is the person's own Hermes calling its
own provider (so inference still leaves the machine under that provider's
policy); Techtree never copies a credential; a comparison is evidence about
one agent on one codebase, never a leaderboard.

Steps, in order: (1) `forge run`, the user's own local Hermes on the built
tasks, baseline arm and candidate arm isolated from each other, the Skill
loaded explicitly; (2) `forge compare`, the two arms side by side per task and
overall with time and usage, shipped as a local report first; (3) qualify the
whole thing in Docker and on a fresh Linux worker the way the task pipeline
was (Docker on the founder's machine was timing out on 2026-09-17 and needs
checking first); (4) publish it as 0.2.1 with an honest changelog entry.

Open founder decisions blocking step 1 (asked in the 2026-09-18 brief, not
yet answered; state them with options and a recommendation every time they
are mentioned):

1. Grading of agent attempts. Options: (a) approve direct Harbor-compatible
   grading now, clearly labelled as such; (b) wait for a demonstrated
   Verifiers handoff. Recommendation: (a), so `forge run` is not blocked on an
   upstream integration; it can be replaced by hard cutover later.
2. Starting state for each arm. Options: (a) fresh empty state for both arms,
   memory off, recorded in the result; (b) each arm's own current state,
   recorded as-is. Recommendation: (a); it is the only version that gives a
   clean comparison, and it is what EvoSkill's freeze step does too.
3. Paid model use. Options: (a) the product uses the end user's own account
   only, and my qualification runs get a fresh small cap (about USD 10, as the
   earlier Prime cap was, of which USD 0.026 was spent); (b) the old cap is
   reused. Recommendation: (a).

## 4. v0.3.0: Techtree Foundry and the first Skill Climb (`techtree-8dj`)

Foundry turns a source bundle into a versioned, isolated environment whose
tasks and verifier are kept apart from the agent under test, and records every
step as a receipt. Slices:

- `8dj.1` source rights: `SourceBundle` binds origin, digest, rights,
  permitted uses, confidentiality and lineage; import refuses missing or
  contradictory rights;
- `8dj.2` environment compilation into a versioned `EnvironmentBlueprint` with
  a receipt binding tools, dependencies, network policy and task material;
- `8dj.3` environment and verifier separation: subjects can never read
  verifier code, answers, held-out data or credentials, and failing the
  declared isolation strength blocks the proving use;
- `8dj.4` explicit development / validation / proving memberships,
  digest-bound and auditable, with receipts stating the real isolation
  strength;
- `8dj.5` validation receipts for environment builds and task sets;
- `8dj.6` search lineage: candidate lineage and search receipts binding parent
  candidates, allowed mutation, prompts or programs, budgets, observed
  development evidence and selection decisions, never proving answers;
- `8dj.7` the first private Skill Climb, blocked by the Market signing, payee,
  authorization and reconciliation contracts;
- `8dj.8` private and executable artifact admission policies;
- `8dj.9` the customer Foundry pilot, plus the narrower approved Repo2RLEnv
  customer service that needs its own qualified recipe but not positive
  uplift.

Separate private proving (the customer's held-out set never leaves their
boundary) ships with Foundry, not before. The v0.3.x studies (`techtree-5t7`:
Prime Agent, prime-rl, model uplift, harness artifacts, Fabric Harness Climb,
Relay cross-harness metrics, environment quality and utility) are deferred
until Foundry and Skill Climb evidence exists.

## 5. EvoSkill v2 and how it can help us directly

Repository: `https://github.com/sentient-agi/EvoSkill/tree/v2` (Apache-2.0,
Python 3.12+, uv, Docker; about 1200 stars; last pushed 2026-08-24). I read
the README, the layout and the module names; I did not run it.

### 5.1 What EvoSkill v2 is, in our terms

EvoSkill evolves a Skill (a markdown tree, like ours) for a fixed agent
against a benchmark, using three agents: a solver (the subject, run through
OpenRouter), an evolver (edits the Skill, run through a Claude Code
subscription with `ANTHROPIC_API_KEY` stripped by `subscription_env()`), and
an agent orchestrator. One epoch is: freeze the instrument, roll out the
solver over three samples, evolve using training digests only, measure on a
validation split and promote every edit, then run the held-out test once.
Benchmarks are τ³-bench banking and SpreadsheetBench v2. Published results:
SpreadsheetBench debugging went from 3 to 21 of 120; τ³ showed no separation;
a three-epoch evolution costs about USD 27, about USD 0.025 per episode.

The parts that matter to us, with where they live:

| EvoSkill piece | Where | Techtree equivalent today |
| --- | --- | --- |
| Comparability gate `compare_runs()`: fifteen instrument fields plus split hash, sealed-test flag and sample count must match before two runs may be compared | `src/orchestrator/comparability.py` | Already stronger in Techtree: `manifests/compare.py` diffs the two variants' canonical bytes and refuses any difference outside the Campaign's mutation contract (and refuses no difference at all); `compatibility.py` does the same for reproductions under a declared drift policy. `forge compare` must reuse these, not add a third comparator. |
| Freeze → rollout → evolve → measure → test-once epoch loop | `src/orchestrator/loop.py`, `evolver_dispatch.py` | `uplift` (one propose-and-measure step, no loop), and the v0.3 `8dj.6` search lineage design. |
| Training / validation / held-out split with a sealed test set | `spec.py`, `brief.py` | v0.3 `8dj.4` memberships. Not in v0.2. |
| Content-addressed replay cache | `src/cache/` | Content-addressed catalog, Skill cache and engine installs (`paths.py`), but no episode replay cache. |
| Evolver containment via macOS `sandbox-exec`, Linux only by recorded opt-out | orchestrator | Techtree runs task material inside Docker on every platform (`forge/docker.py`); Techtree's boundary is stronger and portable. |
| Human gates with sha256 receipts | orchestrator | Signed receipts and approvals; same idea, ours are signed rather than hashed. |
| Leak patterns and Skill integrity checks | `leak_patterns.py`, `skill_integrity.py` | Integrity: every Skill is content-addressed and re-verified file by file (`skills/archive.py`). Leaks: the plugin refuses answer-table *shapes* in a proposal (`plugin/cli/guards.py`); since 2026-09-19 the CLI also refuses any candidate Skill that contains a proving input of the reference taskset, on both preparation paths (`skills/service.py`, `uplift/public_tasks.py`). |
| Phoenix (Arize) tracing | `tracing.py` | None; we retain raw logs and validation output per task. |
| Quota scoping per run | `quota_scope.py` | Open decision 3 above. |

### 5.2 Ideas to take (ordered by value to the v0.2.x lane)

1. **Keep one comparator, and make `forge compare` use it.** Techtree
   already has what EvoSkill's comparability gate does, and more strictly:
   `manifests/compare.py` walks the two variants' canonical bytes and refuses
   any difference outside the Campaign's mutation contract. `forge compare`
   must describe its two arms as a Campaign and two manifests and go through
   that check; the only new work is the forge-specific fields (repository
   revision, task-set digest from the build, Hermes profile and provider,
   seeds) becoming part of the Campaign so the existing walk covers them. Use
   `comparability.py`'s field list only as a checklist for what the forge
   Campaign must carry.

2. **Leak checks on candidate Skills.** Done for the reference taskset on
   2026-09-19: `climb prepare` and `uplift prepare` both refuse a Skill that
   contains any of the taskset's proving inputs (case-insensitive whole
   words), with the offending file and words in the refusal. Unknown tasksets
   are not scanned, by the same lookup-not-inference rule as decision R1.
   For `forge` tasks the equivalent is: refuse a Skill containing the
   reference patch, the failing test names or the test bodies of the build
   it was measured on; that belongs with `forge run`. Both become a
   mandatory gate for `8dj.6`.

3. **Turn `uplift` into an epoch loop for `forge` tasks.** Once `forge run`
   exists, an EvoSkill-style loop is: freeze (already what a `CampaignSpec`
   is), roll out on the training slice, evolve with the evolver seeing only
   training digests, measure on validation, keep or drop the edit, and only at
   the end run the held-out slice once. `forge build` already produces the
   tasks; the split assignment is a per-task label in the build record; the
   evolver is the existing `uplift` proposer. Every promotion decision becomes
   a lineage receipt, which is exactly `8dj.6`, so building it here first
   means v0.3 inherits a proven loop instead of a design.

4. **Adopt the sealed-test rule as a claim rule.** EvoSkill's "test once"
   discipline maps onto our claim surfaces: a result may say "held-out" only
   if the held-out slice was executed exactly once per candidate and the
   receipt says so. That is a guarded sentence on the site and a field in the
   receipt, not a new subsystem.

5. **Replay cache for rollouts.** Cache episode outputs by (instrument
   digest, task digest, seed, arm). It makes repeated `forge compare` runs
   during a Skill revision cheap and makes the "duplicate run" case honest
   (a replayed episode is marked replayed in the receipt, never presented as a
   fresh sample).

6. **Cost accounting per episode.** EvoSkill reports about USD 0.025 per
   episode and USD 27 per evolution. Our receipts should carry measured
   tokens and cost per task and per arm so decision 3 (spend cap) can be
   enforced by the tool and reported truthfully in the changelog.

### 5.3 What we can offer EvoSkill, and where the code could join

- **Techtree as the frozen instrument and signed publication layer.**
  EvoSkill hashes its gates; Techtree signs whole receipts and verifies them
  offline. An EvoSkill epoch record could be wrapped as a Techtree run so
  anyone can verify the before/after claim without trusting the operator.
  Concretely: a small exporter in EvoSkill that emits a Techtree
  `CampaignSpec` plus per-episode results in our canonical JSON, and
  `techtree proof verify` on the other end. No changes to our schemas are
  needed for the public climb shape; a new campaign kind would be needed for
  τ³ or SpreadsheetBench tasks.
- **Portable containment.** EvoSkill's evolver sandbox is macOS-only. Our
  Docker-based task runner (`cli/src/techtree/forge/docker.py`) and the v0.3
  environment/verifier separation give a Linux answer. If they want it, the
  runner is the piece to extract, not the CLI.
- **Repo2RLEnv tasks as an EvoSkill benchmark.** `forge build` produces
  proven repair tasks with a control and reference result for each. Those are
  a ready-made, verifiable benchmark for their solver, one where the
  "did the Skill help" signal is a real test suite rather than a rubric.

### 5.4 What not to take

- Do not vendor EvoSkill. The licence allows it, but their orchestrator
  assumes a Claude Code subscription for the evolver, OpenRouter for the
  solver and Phoenix for tracing; none of that fits our "subject is the
  person's own Hermes" rule or our no-credential-copy rule.
- Do not import their "promote every edit" policy as-is; in our model a
  promotion is a lineage receipt that a human or an explicit policy signs.
- Do not present any EvoSkill-derived loop as qualified until it has been
  reproduced end to end under our own rules; their τ³ result showing no
  separation is a reminder that the honest outcome is often "no effect".
