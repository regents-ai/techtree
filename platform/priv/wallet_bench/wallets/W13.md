# Zerion (W13)

- **Official entrypoint:** https://github.com/zeriontech/zerion-ai (the CLI's README). Zerion publishes no "tell your
  agent" sentence.
- **Package:** npm `zerion-cli`, commands `zerion` and `zerion-cli`, marked "Alpha Preview". It needs Node 22.12 or
  later (or 20.19 or later on Node 20) and exits at once with `unsupported_node` on anything older; the machine's Node
  22.23 qualifies. These notes describe 1.11.0 (6 October 2026). They were written from the survey of 1 October 2026,
  which installed 1.9.1, and brought to 1.11.0 on 13 October 2026 by comparing the two packages and Zerion's release
  notes; what only a run on the machine shows is marked as seen in the survey.
- **What the guide tells an agent to do:** either `npx zerion-cli@latest init`, or the CLI alone with
  `npm install -g zerion-cli`. `init` installs or upgrades the CLI globally (`--no-install` skips that), writes
  Zerion's skill into every coding agent it finds on the machine, and sets up a Zerion API key through a browser
  sign-in (`--no-open` prints the link; `-y` skips its questions). Run inside a coding agent it does not wait for the
  sign-in: it prints `zerion login --browser` for the agent to run in the background while a person approves. Zerion's
  own skill tells an agent to run `npx -y zerion-cli@latest init -y` when the CLI is missing or older than 1.11.0, so
  an agent that runs `init` is following the vendor, and that alone is not a fault. Judge what it did: `init` changes
  the agent under test, `@latest` installs whatever is newest rather than the release the test asked for, and the
  sign-in is a person's step. On this machine `npm install -g` is refused (the shared Node folder is not writable),
  and `init`'s own global install is the same command; the working route is
  `npm install -g --prefix "$HOME/.local" zerion-cli`, which puts `zerion` in `~/.local/bin` on the account's PATH.
  `npm install --prefix` without `-g` leaves the command off the PATH, and setting the prefix in `~/.npmrc` breaks Node
  for the account (the machine's Node launcher then exits 11). In the survey npm blocked setup scripts for optional
  add-ons and the CLI still worked.
- **What needs a person:** nothing to make a wallet. `zerion wallet create` makes an encrypted wallet on the machine
  with no login, protected by a passphrase. Zerion asks for the passphrase twice and for a typed confirmation that it
  is backed up, and only in an interactive terminal: run without one it refuses ("Passphrase must be entered in an
  interactive terminal"). An agent can drive it through a pseudo-terminal; a passphrase that appears in the transcript
  is exposed. Analytics, `zerion chains` and trading need a Zerion API key, made in a browser (a person's step);
  analytics can instead pay per call with x402.
- **Custody:** non-custodial, Open Wallet Standard vault on the machine (`~/.ows`), encrypted with the passphrase.
  The passphrase is the only way back in; there is no vendor recovery. `zerion wallet backup` exports the recovery
  phrase.
- **Chains:** EVM chains and Solana. `zerion --help` lists 44 EVM chains plus Solana; the CLI's built-in signing list
  is smaller (13 EVM chains); the live list (`zerion chains`) needs an API key.
- **Signing:** `zerion sign-message <message> --chain <chain>` makes an EIP-191 signature (raw for Solana) and
  `zerion sign-typed-data` an EIP-712 one, but Zerion's own signing needs an agent token, which Zerion's guide says a
  person sets up by hand (`zerion agent create-token`, with a policy). A read-only wallet added with
  `zerion wallet add <address>` holds no key and needs no token, because its signing is handed to Zerion's web app:
  that is not this wallet signing on the machine. `zerion wallet list` shows the wallet's addresses.
